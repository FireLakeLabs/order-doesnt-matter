# Timing qualifications

No speed comparison or production latency verdict is made. This is the requested
ballpark cost of the completed synchronous import/generate transformations.

Node v24.22.2, npm 11.19.1, 16 logical CPUs; exact dependency versions are locked.
Observed shared-machine load was 0.43/0.21/0.12 before the final pass setup and
0.67/0.76/0.45 after it. Other agents, Node/tsx, Chrome and headless Chrome were
active and left running. JIT/GC and those processes affect these small samples.

`study.ts` reads each of the 72 real fixture files once, discards one warm
import/generate pair, then collects seven samples per operation. Even rounds
import then generate; odd rounds generate the preceding identical document then
import. Only the synchronous function call is timed; every returned document and
generated string is checked outside the timed interval against the warm output.
The last results are serialized, reimported and queried against the original.
There are no dropped error samples or asynchronous/lazy operations inside the
regions. Zero imports/generations throw; three event comparisons remain
qualified as documented in FINDINGS. The slowest import program median is the first fixture, micro-tree-stack; the
slowest generation median is piece-paper-lantern. Residual warmup is plausible. These are not cold
startup or p95 latency measurements.

`results.json` stores all seven raw samples per program. `TIMINGS.md` lists both
median and worst individual sample per program. The FINDINGS cost table reports
the median across the 72 program medians, the largest program median and the
largest individual sample; these are different statistics.

A separate diagnostic run uses `profile.ts`: sixty passes across all 72 files,
consuming generated byte lengths. Invoke with:

```sh
node --cpu-prof --cpu-prof-dir=profile --import tsx profile.ts
```

Its saved profile/hotspots show garbage collection (375 direct samples), PEG mini
parsing across many contexts, and AST/document traversal. Allocation/parsing CPU
is the practical limiter in this unoptimized spike. Node/tsx loader activity is
also present in that diagnostic and is not a production-runtime comparison.
Profile timings are not reported as import/generate timings.

No tuning comparison was attempted. Worker startup, Strudel imports, event
querying, serialization, browser bundling, editor rendering, sample decoding and
audio scheduling are outside the timed regions. End-to-end edit-to-audible
latency was not measured. Fast transformations do not establish glitch-free
playback. No performance thresholds are imposed on tests.
